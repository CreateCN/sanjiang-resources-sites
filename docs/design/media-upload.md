# 设计：资料图片上传与媒体库

> 状态：**P0 已实现（2026-10-22）**；§14 已合入 [SECURITY-SPEC](../security/SECURITY-SPEC.md) v1.5。
> 迁移：`009-media-library`（已应用）。P1（媒体选择器、自动 GC 维护任务、跨环境登记、显式缺图移除导入）与 P2 未实现。
>
> 实现相对本文的差异（均不削弱约束）：
> - **`/media/` 由中间件短路服务**（`src/server/media-http.ts`），不使用 `src/pages/media/[...name].ts`：项目启用 `trailingSlash: 'always'`，带扩展名的文件路由会被当作缺尾斜杠的页面而落到 404。中间件在路由解析前处理，URL 保持 `/media/<sha256>.webp`；GET/HEAD 每次查库，所有响应 `no-store`。
> - 上传入口只有资源编辑页（P0）；`/admin/media/` 是最小管理员入口（下架/恢复/彻底删除 + 用量），不含选择器、批量与 GC。
> - `MEDIA_BUNDLE_MAX_BYTES` 只能通过环境变量**收紧**（默认 32 MiB 硬上限）。
> - 缺图导入 P0 只做"逐条拒绝"；显式移除（`dropMissingMedia`）按交付阶段留给 P1，`stripUnavailableMedia` 作为纯函数已就绪但未接入导入流程。
> - 媒体目录、操作占位、配额与对账脚本：`src/server/media.ts`、`scripts/reconcile-media.mjs`；站点备份/恢复：`scripts/backup-site.mjs`、`scripts/restore-site.mjs`（共享 `src/server/restore-prepare.ts`）。

## 1. 现有约束与核心取舍

| 约束 | 方案 |
|---|---|
| Docker 运行镜像没有 `public/`，`image-variants.json` 是构建期产物 | 文件放 `MEDIA_DIR`（默认 `./data/media`，容器 `/app/data/media`），由运行时路由服务；上传媒体从 DB 查变体 |
| `ResourceSchema.image` 是 JSON 中的字符串，历史修订可以恢复 | 保持字符串；写入与发布校验依赖；当前内容及历史修订都保护媒体免遭清理 |
| Markdown 已允许站内图片 | 语法白名单新增 `/media/`；提取引用与实际渲染共用 Markdown token 解析，不能只扫描 `image` 字段 |
| 管理写操作统一 Origin、CSRF、角色和审计 | 上传、下架、恢复、彻底删除均走 `/api/manage/`；维护任务复用相同存储规则 |
| 下架要阻止后续请求继续获取图片 | `/media/` 成功及错误响应均 `Cache-Control: no-store`；禁止代理/CDN缓存、`alias` 直出；不宣称能收回用户已下载的副本 |
| 图片和 SQLite 同卷 | 配额按全部媒体文件计费，预留空间后才能落盘；备份与恢复是 P0 上线门禁 |

内容摘要用于身份、去重和完整性校验，**不意味着可以覆盖或删除共享文件，也不意味着必须长期缓存**。`/_astro/` 的静态缓存优化不属于此功能的必需改动。

## 2. 范围与权限

- admin、editor 可以上传本地 PNG/JPEG/WebP；拒绝 SVG、GIF、动图、远程抓取及代理下载。
- 服务端校验 magic bytes 与解码结果，按 EXIF 方向旋转后重编码 WebP，移除 EXIF/GPS/XMP 等元数据，生成多档变体。
- 编辑页“移除”只清空当前草稿的图片关联，仍需保存；不会下架共享媒体，也不会直接改变公开快照。
- 全局下架、恢复下架、彻底删除仅 admin 可操作，均需要目标媒体 `version` 和审计。
- 首批不提供在线裁剪、滤镜、公开上传或图像编辑。

## 3. 数据流与 HTTP 入口

```text
multipart /api/manage/ action=upload-media
  → requireOrigin → requireSession → 限量读取 multipart → requireCsrf
  → 重新读取操作者角色 → 账号限流 → 获取全局媒体操作占位及空间预留
  → 校验、转码、生成变体 → 私有暂存目录 → 原子安装完整文件组
  → 事务内登记媒体 + 审计 + 释放预留/操作占位
  → JSON 返回 src/尺寸/变体 → 编辑器回填隐藏字段 → 另行保存草稿
```

- 文件上限 `IMAGE_MAX_BYTES = 5 MiB`；multipart 上限为 `5 MiB + 64 KiB`，只接受一个文件；其余字段数量和长度有上限，未知字段拒绝。`rights` 仅 confirmed/unconfirmed，`credit` 最长 300，confirmed 必须有署名；原文件名去控制字符并截断。
- `managePost` 硬读取上限取上传与导入上限的较大值；读到 action 后分别收紧到上传、导入、普通表单原有上限。普通动作仍为 96 KiB，导入仍沿用当前上限。
- 修改上限前先验证会话；CSRF 仍必须在表单解析后验证，任何图像解码、磁盘写入之前完成授权。代理使用 `client_max_body_size 6m` 并保留请求连接与超时限制。
- 上传计数 `media-upload` 每账号 20/h；全站一次只允许一个改变媒体存储的操作，包括跨 app/maintenance 进程。占位忙时返回 503 + 短 `Retry-After`，不在内存排无限队列。
- 文件为空、单文件超过 5 MiB、伪造 Content-Type、额外大文本字段都必须独立拒绝。
- P0 的上传按钮依赖本站 JS，使用独立表单，避免与资源编辑表单嵌套。无 JS 时给出明确提示；不得根据任意查询参数自动替换草稿的图片。

## 4. 文件布局与不可变边界

对重编码后的主图计算 `id = sha256(master)`；同一编码版本、同一输入可以复用同一文件组。

```text
media/
├── objects/<64hex>/
│   ├── master.webp
│   ├── 320.webp
│   ├── 640.webp
│   ├── ...
│   └── manifest.json
└── staging/<operation-uuid>/
    └── bundle/                 # 完整构建后，rename 为 objects/<id>
```

- 公共 URL 保持 `/media/<id>.webp`、`/media/<id>-320.webp`，内部布局不暴露给用户。清单记录每个文件的字节数、尺寸、sha256 和编码版本。
- 根目录、对象目录和暂存目录 0700，文件 0640；只允许应用服务账户写入。源文件名仅作截断后的展示值，不参与路径拼接。
- 主图和变体作为一个目录原子安装，避免半套变体对外可见；安装后不可覆盖。已存在对象目录绝不通过 `rename`/`unlink` 替换。
- 重复上传只校验并复用原文件组，不改其署名、权利状态或下架状态。下架或命中 purge 墓碑的同图返回 409，提示联系管理员；普通上传对 admin 也不隐式恢复。
- 编码器升级后可能得到不同摘要；若已存在相同主图摘要，以原变体清单为准，不在上传时重写变体。

## 5. 数据模型（迁移 `009-media-library`）

以下为实现契约；DDL 还须沿用现有迁移的幂等检查和约束风格。

| 表 | 字段及约束 |
|---|---|
| `media` | `id`（64 hex 主键）、`version`（正整数，默认 1）、`state`（`ready`/`purging`）、`bytes`（主图）、`total_bytes`（整组含清单）、`width/height`、`variants`（含每档 bytes/hash）、`encoding_version`、`source_name`、`uploaded_by`、`rights`、`credit`、`created_at`、`deleted_at/deleted_by/deleted_reason` |
| `media_tombstones` | `id`（摘要主键）、`last_version`、下架原因与操作者；purge 后保留，防旧表单版本复用及同图自动重新上架；不保存图片字节 |
| `media_operations` | `id`（随机 UUID 主键）、`kind`（upload/purge/reconcile）、`media_id`（可空）、`phase`、`reserved_bytes`（非负）、`owner`（进程启动随机身份）、`created_at/updated_at`、失败分类；禁止记录凭据或原始图片内容 |
| `media_store_guard` | 固定一行，`operation_id` 可空，指向当前独占操作；通过 `BEGIN IMMEDIATE` 检查并获取/释放，不用进程内变量充当跨进程锁 |

- 下架状态与 `state` 独立：`ready + deleted_at` 保留文件与历史引用，但不对外服务。
- 有效引用只能指向存在的文件组；新写入依赖检查、引用扫描、标记 `purging` 必须直接读事务中的 DB，不使用可能已过期的请求 memo。
- 操作记录只在物理文件和账目核对完成后删除；失败记录保留用于恢复与对账。
- **没有按时间自动抢占的锁租约。** 进程异常退出后占位保留，上传/清理暂停、公开页继续工作。运维先停止所有媒体写入者，再运行离线对账，不能只根据 PID 或超时断定另一个进程已停止。

## 6. 上传、配额与失败恢复

### 6.1 输入与编码

```ts
IMAGE_MAX_BYTES = 5 * 1024 * 1024;
IMAGE_MAX_PIXELS = 40_000_000;
IMAGE_MIN_EDGE = 200;
IMAGE_MAX_EDGE = 5000;
VARIANT_WIDTHS = [320, 640, 960, 1280, 1920];
MEDIA_BUNDLE_MAX_BYTES = 32 * 1024 * 1024;
MEDIA_QUOTA_BYTES = 512 * 1024 * 1024;
MEDIA_MIN_FREE_BYTES = 128 * 1024 * 1024;
```

magic bytes → `sharp(..., { limitInputPixels, failOn: 'error', animated: false })` → metadata：只允许 PNG/JPEG/WebP，拒绝多页/动图，边长 200–5000，宽高比 1:4–4:1。`.rotate().webp({ quality: 82, effort: 4 })` 输出主图，变体 quality 80、禁止放大；输出尺寸以旋转后的结果为准。输出逐段计数，整组超过 32 MiB 即中止。不能只限制压缩输入而让输出无限增长。

### 6.2 容量定义

- 逻辑预算：`所有 media.total_bytes（含下架、purging） + 所有未结算 reserved_bytes <= MEDIA_QUOTA_BYTES`。
- 每次上传先在获取操作占位的同一事务中预留 32 MiB，再解码和写暂存文件；不足返回 507，无磁盘副作用。此保守预留可能拒绝接近配额时的小图，P0 接受该取舍。
- 预留覆盖暂存与最终对象：同分区目录 rename 不复制文件。原始上传缓存在受请求上限约束的内存中，不另写未计费磁盘文件。
- 下架不释放配额；只有实际物理删除且对账成功才释放。遗留对象/暂存文件在离线对账前由原预留覆盖，不可因请求失败就先清零。
- 落盘前检查可用空间，须保留 `MEDIA_MIN_FREE_BYTES` 给 SQLite 等服务；不足或检查失败则拒绝上传。此保留值不是对同卷其他程序写入的保证，部署仍需磁盘告警。

### 6.3 提交与补偿顺序

1. 已完成授权、限流；事务内取得操作占位及容量预留，并登记操作 ID。
2. 在该操作专属暂存目录生成完整 bundle，写清单、fsync 文件及目录；尺寸/输出体积不符则中止。
3. 计算主图摘要：若已有 `ready` 且未下架的同图，校验原清单/文件后复用，只移除本操作暂存文件；事务内再次核对操作者和媒体有效状态、写重复上传审计并释放预留与占位。原媒体信息不被重复上传覆盖。
4. 若命中下架资产或 purge 墓碑，409；禁止自动复活。若出现未登记的最终目录或未完成操作，停止并要求对账，禁止覆盖或自行认领。
5. 新对象：先持久化操作的 `media_id` 与清单摘要，再把完整暂存 bundle 原子安装到不存在的最终目录，fsync 父目录；更新阶段为 installed。
6. 最终 `BEGIN IMMEDIATE` 中重新读取操作者有效状态/角色；验证操作仍归本请求，插入 `media`、写 `upload-media` 审计，将预留转为实际 `total_bytes`，释放占位并结算操作。**审计失败同事务回滚，媒体不可见。**
7. 只有第 6 步成功才返回可引用路径。业务事务不得跨越 sharp/文件 I/O 的 await。

**失败与崩溃规则：**

- 可以立即清理的只有操作自己的 `staging/<operation-id>`；物理清理成功后才释放相应预留。
- 已安装到 `objects/` 的目录一律不在请求 catch 中删除，不论是重复上传还是新图。安装后提交失败保留操作记录、容量预留与占位，由离线对账决定补偿；不会误删别的请求已提交的文件。
- 离线 `scripts/reconcile-media.mjs` 必须确认所有 app/maintenance/手动媒体任务均停止，核对 DB、操作记录及实际哈希。已提交资产只校验，不删除；未提交对象保全到受计费的隔离区并报告，显式确认后可删除。孤儿也不能静默丢弃。
- 对账重建容量账目，处理本次明确记录的暂存/孤儿后才释放占位。记录指向不明、哈希不符或文件缺失则保持上传暂停，输出可操作错误。P0 必须提供此命令及演练。

## 7. 运行时服务与缓存

`src/pages/media/[...name].ts` 接受的公共文件名：

```ts
/^[a-f0-9]{64}(?:-(320|640|960|1280|1920))?\.webp$/
```

处理顺序：拒绝查询串与非法名字 → 查 DB（存在、`state=ready`、未下架）→ 确认所请求变体在清单中 → 映射到受控内部文件名 → 验证路径位于 MEDIA_DIR 内、拒绝符号链接/非普通文件 → 返回 WebP。`HEAD` 与 GET 共用判定。DB/文件故障 fail-closed，不泄漏磁盘路径；已下架或不存在统一 404。

所有成功、404、错误响应均包含 `Cache-Control: no-store`，WebP 响应另带 `Content-Type: image/webp`、`nosniff` 和 inline disposition。不返回绕过可用性检查的 304。保持现有中间件默认，不给 `/media/` 开长缓存例外。

反代/CDN 必须转发到应用并禁用此路径缓存，**禁止 `alias`/`root` 直出媒体卷**。下架提交后开始的新请求均拒绝；已经开始的响应、已下载或用户保存的副本无法追溯撤回，文案必须如实说明。

## 8. 内容接入与引用规则

- `ResourceSchema.image` 保持可选字符串，允许现有 `/images/<安全文件名>` 或 `/media/<64hex>.webp`；带图时 `imageAlt` 必填。
- `siteImageSource` 只做语法白名单；保留无查询串、控制字符、穿越与编码绕过的限制。Markdown 同时支持主图路径；不接受任意站内路径。
- 建立一个权威的 `extractMediaReferences(kind, payload)`：结构化 `image` + 实际会渲染 Markdown 的字段；通过相同 Markdown 解析配置提取图片 token（含引用式语法），再走同一个路径规范化函数。纯文本中的 URL 不算引用。
- 扫描集合：`resources.draft/published`、`guides.draft/published`、资源及指南的全部 `revisions.data`，**包括回收站条目**。如将来 settings 等字段支持图片，增加写入口时必须同步加入扫描。
- 保存、导入、历史恢复、发布统一使用该依赖提取器并在业务事务内校验：新增引用只允许 `ready` 且未下架的媒体。允许仅编辑其他字段时保留当前已有的下架引用，但明确提示；发布必须先显式替换/移除下架或缺失图片。不能用保存绕过下架，也不能静默删关联。
- SSR 的 `ResourceImage` 对 `/media/` 从 DB 取变体（只用于读渲染的 requestMemo），对 `/images/` 查构建清单。已下架/缺失媒体输出带 alt 的占位提示；Markdown 的 SSR 调用层也提供相同可用性判定，不能只退回一个仍指向 404 的 `<img>` 并声称不会裂图。
- 编辑页上传成功只回填 `image/imageRights/imageCredit` 并触发草稿变更提示；修改关联仍走原有版本锁。

## 9. 生命周期、引用保护与 GC

| 动作 | 语义 |
|---|---|
| 草稿移除图片 | 只解除当前草稿引用；保存/发布按既有流程，不改媒体本身 |
| `delete-media` | admin + version + 原因；全局下架、version+1、审计同事务，保留文件与引用 |
| `restore-media` | admin + version + 确认理由；检查清单/文件完整才恢复；编辑者重复上传不能代替此操作 |
| `purge-media` | admin + version；仅已下架且全量引用为零时允许；有引用 409，列出实体、草稿/公开/修订位置 |

下架和恢复也须取得 §5 操作占位；文件检查完成后事务内重查 version，再修改状态及审计。彻底删除同样取得占位，事务内再次扫描引用并标记 `purging`、记录操作及开始审计；内容写入口从此拒绝新引用。之后删文件组；成功后事务内保存摘要与最后版本的下架墓碑、删除媒体行、写完成审计并释放容量/占位。墓碑不参与图片字节配额，也不因清理期限自动消失；同图重新登记须管理员显式审批并延续版本，未提供该恢复流程时一律拒绝重新上传。文件删除或最终审计失败时保留 `purging` 与操作记录，容量不提前释放，离线对账后重试；不能把外部文件删除当作可随 SQL 回滚的操作。

`cleanup-media.mjs` 默认 `--dry-run`；正式模式只处理**已下架满 30 天、无当前或历史引用**的资产，调用同一 purge 流程，并逐项重查。仍被修订引用的媒体永久受保护；180 天也不能覆盖引用保护。未下架但无人引用的图只列候选，不自动删除。未登记文件、暂存残留和中断操作交给离线对账，不按 mtime 直接删。

P1 才接入维护 worker 的 `media` 任务及 `MEDIA_CLEANUP_UTC_HOUR`（默认 UTC 17）；占位忙则跳过并记录，不与上传竞争。

## 10. 导入导出与跨环境迁移

- 内容导出 `schemaVersion: 2` 仅带媒体元数据和完整性清单，不含二进制、内部操作记录或物理路径；导出不是完整备份。
- 复制目录不会自动创建可用媒体记录。跨环境路径为：复制文件至隔离暂存 → 管理员运行 P1 的 `scripts/register-media.mjs` 离线媒体登记工具，逐文件核对摘要/尺寸/清单、配额与权利元数据，拒绝覆盖或复活目标的下架资产 → 再预检内容导入。整体搬迁优先使用 §11 的站点备份恢复。
- 预检按所有引用核对 DB 及文件可用性，冻结相关媒体的版本/下架状态和缺失清单。应用时事务内再校验；有效目标变化按现有预检冲突规则拒绝，不能临提交才改变确认态。
- 缺媒体默认将对应条目标为无效，不写入；其他合法条目仍按原有逐条语义导入。只有显式勾选 `dropMissingMedia`，才按预检展示的修改清单移除对应 `image` 或 Markdown 图片节点（保留 alt 文本），并报告逐条警告。勾选状态绑定预检摘要；不允许默认清空或静默更改内容。

## 11. 首批备份与恢复门禁

- P0 新增 `scripts/backup-site.mjs` / `scripts/restore-site.mjs` 站点级备份/恢复工具，复用现有 DB 完整性校验，打包 DB + 全部已登记对象（含下架资产）+ 文件哈希清单。原 `db:backup` 仍可作数据库诊断快照，但不得称为媒体站点的完整备份。
- P0 先采用**离线一致性备份**：停 app、maintenance、定时与手动写入者 → 对账到无未完成操作（快照中的媒体占位必须为空）→ 生成同一批次 DB 快照和媒体包 → 校验所有登记对象哈希/体积 → 原子标记批次完成。不能用两个独立定时任务的时间戳推断一致性。
- 不完整、缺文件、未知 schema 或哈希不符的备份不能标记成功，也不能替换现有可用目标。密钥、身份凭据与备份分开保存。
- 恢复同样离线：在目标卷的暂存位置完整验证 DB 与媒体、空间、路径及清单 → 保全现有 DB/sidecar/媒体 → 受恢复日志保护地切换 DB 和媒体 → 核验所有引用 → 才允许启动。DB 与目录不是单个原子 rename，故中途退出后须根据日志完成回滚/恢复，不能启动混合批次。
- 首批必须演练：普通恢复、缺图拒绝、哈希不符、恢复中途故障回滚，以及“DB 完整但媒体缺失”不能算成功。部署后启用磁盘空间告警。
- 若已安装 TOTP，恢复流程复用 [TOTP §10](totp-2fa.md#10-恢复与运维p0) 的暂存迁移与认证净化；现有 `restore-db` 发现 DB 含媒体登记时必须拒绝 DB-only 的完整站点恢复，指向 restore-site，避免旧入口制造 DB/媒体混合批次。

## 12. 错误与运维配置

- 400 格式/尺寸/字段错误；413 请求或文件体积超限；415 不支持的编码；403 越权；409 版本、下架或引用冲突；429 账号上传过频；503 操作占位忙/需对账；507 媒体预算或实际磁盘余量不足。
- 配置：`MEDIA_DIR`、`MEDIA_QUOTA_BYTES`、`MEDIA_MIN_FREE_BYTES`；P1 才增加清理时刻。`MEDIA_BUNDLE_MAX_BYTES` 为集中定义的编码输出上限。
- Docker 同卷保留，补目录权限；代理体积上限 6m，媒体缓存与直出关闭。存储不可写/操作未结算只禁用媒体写入，后台其他功能继续可用；状态页明确显示待对账原因。

## 13. 验证与验收

单元/集成 `tests/media.test.mjs`：

1. 三种允许输入、旋转后尺寸、WebP 变体及元数据剥离；伪装 SVG/HTML、动图、截断图、过小/过大/极端比例、输出超过 32 MiB 拒绝。
2. 文件 5 MiB、multipart 总上限、多个文件、普通表单原上限、导入原上限分别验证；越权/CSRF/Origin 在解码和文件写入前拒绝。
3. 已有公开引用 + 重复上传 + 审计失败，原文件及公开响应保持正常；两个进程上传同图只有一个安装者，另一方可重试复用，失败请求绝不删共享对象。
4. 在暂存、目录安装、DB 最终提交、释放占位各边界注入故障；失败预算不提前释放；重启后不自动抢占，离线对账保全或修复并恢复写入。
5. 主图+变体+下架文件+未结算预留总计费；并发不能超额；低磁盘余量拒绝；物理清理完成前配额不释放。
6. 结构化字段、资源 Markdown、指南 Markdown（含引用式图片）、全部修订及回收站引用都阻止 purge/GC；媒体进入 purging 后不能新增引用。
7. 资源页移除只影响草稿；编辑者上传下架同图不能复活；admin 恢复须版本/理由且文件完整；不存在与下架统一 404。
8. 路由穿越、符号链接、未声明变体、大小写哈希、查询串拒绝；GET/HEAD 一致；所有响应 no-store；代理/CDN也不得缓存/绕过 DB。
9. 导入缺图默认逐条拒绝；显式移除保留 alt 并报告；预检后媒体状态或选项变化需重新预检；仅复制目录不视为已登记。
10. 全站备份恢复演练及失败回滚（§11），不以 DB 的 integrity_check 代替媒体完整性校验。

真实浏览器/HTTP：上传→回填→保存草稿→发布→变体加载；Markdown 引用；草稿移除不影响其他条目；下架后旧 URL 新请求拒绝、页面占位；备份恢复后公开页和历史恢复都有图。CI 使用临时 DB/MEDIA_DIR，禁止触碰现存数据卷。

## 14. SECURITY-SPEC 增补草案（实施前合入）

- §3.4：仅允许经 magic bytes/解码双重验证并重新编码的本地 PNG/JPEG/WebP；拒绝动画和 SVG；限制输入、输出、像素、边长与比例，移除隐私元数据。
- §3.4/§5.1：不可变文件组只安装一次；失败只能清理本操作暂存；跨进程持久操作占位及配额预留；不得在请求 catch 中删除共享最终文件。
- §5/§5.1：解除引用、下架、恢复、purge 分开授权；媒体写操作绑定版本；所有业务变更与对应阶段审计同事务。
- §5.1：当前资源/指南、Markdown 与全部可恢复修订共享引用提取器；有引用禁止物理清理；删除冻结状态后拒绝新引用。
- §6：媒体所有保留文件、变体及未结算操作均计费；预留后落盘，物理删除完成后才释放，保留实际磁盘安全余量。
- §8/§9.2：`/media/` 必须经过实时状态检查并 no-store，禁止缓存或代理直出绕过下架；明确无法收回已下载副本。
- §8/§9.5：DB+媒体同批离线备份与可回滚恢复、故障注入和恢复演练为上传上线门禁。
- §11.1：加入 §13 全部安全场景；覆盖跨进程并发、审计失败、崩溃、下架与恢复。
