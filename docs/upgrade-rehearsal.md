# 升级回滚演练记录

日期：2026-10-23

脚本：`bash scripts/upgrade-rehearsal.sh`（可重复）

| 项 | 值 |
|---|---|

候选版本使用工作树构建，是为了在实际提交/打 tag 前完成演练；正式发行仍必须使用完整 SHA 与固定 digest。

## 2. 步骤

1. 用 `git worktree` 导出旧提交，构建旧镜像；构建候选镜像。
2. 旧版本在干净卷启动，写入 12 条种子资源，创建管理员 `legacyadmin`，验证登录。
3. 停旧 app，用**旧版本** `backup-site.mjs` 做停写整站备份，检查 `COMPLETE`、数据库哈希与计数。
4. 候选版本在**同一数据卷**启动，自动应用 011/012；验证健康、首页资源、旧管理员登录。
5. 候选版本写入一条仅升级后存在的赞助，作为回滚应丢失的数据。
6. 停写复制数据，候选镜像以 `--network none` 启动，容器内请求健康与首页，验证无外部网络也能运行。
7. 停候选，用**旧版本** `restore-site.mjs` 恢复升级前备份。
8. 启动旧版本，验证旧数据、旧管理员登录、旧会话失效与 schema 回到 010。

## 4. 结论

- 本次演练采用**数据恢复**回滚：旧工具恢复升级前 DB+媒体批次，再启动旧程序；没有把升级后的数据库直接交给旧程序。
- 旧版本 `866a75f` 没有“未知迁移拒绝”保护；仅换回旧镜像可能启动并忽略新表/新字段，不能作为受支持的程序回退。本演练未使用该路径。
- 恢复会丢失备份后的写入（候选赞助），并撤销会话/挑战/恢复码；必须保留原 `TOTP_ENC_KEY`。
- 候选镜像在无网络下可完成健康与首页读取，说明发行物本身不依赖中央服务；外部资源链接、主动链接检查不在此结论内。
- 媒体对象未参与本次数据（旧版本种子无媒体）；媒体同批复核由 P1-05 的备份/恢复测试与 `container-smoke.sh` 覆盖。

## 5. 复现

```bash
npm run rehearsal:upgrade
```

要求：Git、Docker、curl、Node 24；本地存在旧提交 `866a75f`。脚本使用临时 worktree/目录/容器，不推送、不创建 tag、不修改工作树。
