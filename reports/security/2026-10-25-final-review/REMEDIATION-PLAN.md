## 1. P1：修复不可信身份下恢复码失败不计数

### 原因与影响

`src/server/auth.ts` 的 `verifyLoginChallenge()` 使用 `rules[2]` 选择恢复码失败规则。可信身份包含客户端规则时下标成立；`unverified` 身份不生成客户端规则，恢复码规则移到下标 1，导致取到 `undefined`。

错误恢复码进入 `settleChallengeFailure()` 时抛出 `TypeError`，HTTP 返回 500，恢复码失败额度和挑战尝试次数都不增加。独立临时库连续提交 7 次格式正确的错误恢复码 `AAAA-BBBB`，挑战始终 `attempts=0`、未消费，且没有恢复码限流桶。攻击者取得有效登录挑战后，可以在有效期内持续猜测。

### 修改方案

修改 `src/server/auth.ts`：

1. 分别定义具名的 TOTP 账号规则和恢复码账号规则，类型使用现有 `LimitRule`。
2. 构造检查规则数组时引用上述变量，客户端规则仍由 `clientLimitRules()` 按身份生成。
3. 根据输入类型直接选择具名规则传给 `settleChallengeFailure()`，删除依赖数组位置的 `rules[2]` / `rules[0]` 选择方式。
4. 保留现有失败结算事务、成功消费恢复码事务、账号与客户端预算，以及不可信身份不创建客户端桶的语义。

### 回归用例

在 `tests/totp-server.test.mjs` 增加用例，使用独立数据库，覆盖 `client` 与 `unverified` 两类身份：

- 启用 TOTP，取得有效登录挑战；提交格式正确但数据库中不存在的恢复码。测试生成该值后确认它不等于任何实际恢复码，避免随机碰撞。
- 前 3 次错误恢复码返回 401；恢复码账号桶计数依次为 1、2、3，挑战 `attempts` 同步增加。
- 第 4 次被账号预算拒绝为 429，不继续增加挑战尝试次数；窗口为 60 分钟。
- 错误恢复码不增加 TOTP 账号失败桶；可信身份正常增加客户端失败桶，不可信身份不创建客户端桶。
- 在未耗尽额度的新场景中，正确恢复码能够登录且只消费一次；复用被拒绝。
- 使用错误 TOTP 覆盖挑战第 5 次失败后作废，避免恢复码 3 次上限提前阻断而无法验证挑战上限。

在 `tests/server.test.mjs` 增加 HTTP 回归：通过无凭据或错误凭据得到 `unverified` 身份，走实际登录挑战与恢复码提交入口，验证 401 → 429、非 500，以及正值且不超过窗口的 `Retry-After`。不能只测试内部抛出的异常。

验收：不存在固定数组下标选规则的逻辑；错误恢复码不能绕过计数；正向登录、恢复码单次消费及挑战作废行为均通过。

## 2. P2：使部署自检的 strict 模式兑现警告升级契约

### 原因与影响

`scripts/check-deployment.mjs` 对生产 HTTP 地址始终记录 `warn`，仅在另一处分支单独使用 `strict` 升级。实测生产 HTTP 地址、代理凭据齐全并带 `--strict` 时，仍输出 `status: ok`、退出码 0，与发布门禁说明不符。

### 修改方案

1. 在 `report()` 中统一执行等级转换：`strict && level === 'warn'` 时保存为 `error`。
2. 删除分支中的重复升级条件，调用处只表达原始等级。
3. 保持普通模式下 HTTP 为警告、缺失或过短代理凭据为错误；保留直连部署在 strict 模式下需要处理转发头风险的既有行为。
4. `status` 与退出码继续从转换后的 findings 计算，不新增第二套失败判断。

在 `tests/deployment.test.mjs` 增加矩阵：

| 环境与配置 | 普通模式 | strict 模式 |
|---|---|---|
| production、HTTP、代理凭据齐全 | warn，退出 0 | error，退出 1 |
| production、HTTPS、代理凭据齐全 | ok，退出 0 | ok，退出 0 |
| 代理凭据缺失或过短 | error，退出 1 | error，退出 1 |
| 直连部署的转发头检查提示 | warn，退出 0 | error，退出 1 |

同时断言 JSON 的 finding 等级、`status`、`strict` 与进程退出码，避免仅检查提示文字。
